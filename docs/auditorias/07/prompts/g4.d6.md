Você é um arquiteto de software sênior conduzindo uma auditoria técnica de aderência entre implementação e especificação.

# Objetivo

Auditar exclusivamente o domínio:

> Integridade relacional (consistência global do banco, coerência entre entidades e garantia de integridade entre dados)

O objetivo é verificar se o sistema mantém integridade de dados em nível global, considerando modelos, migrations, relacionamentos e regras de negócio, garantindo ausência de inconsistências, corrupção de dados e violação de dependências entre entidades.

---

# Escopo EXCLUSIVO desta auditoria

Inclui SOMENTE:

- integridade referencial entre tabelas (FKs reais no banco)
- consistência entre entidades relacionadas
- coerência de dados entre models e migrations
- regras de cascata (delete/update)
- integridade de dados entre eventos, usuários e certificados
- consistência entre dados dinâmicos e estruturas JSONB
- integridade de estado (status de certificados, eventos, usuários)
- validação de consistência pós-CRUD
- dependências entre entidades no nível de dados
- risco de orphan records
- inconsistência entre soft delete e relações
- integridade de enumerações em nível de banco

---

# Fora de escopo

- implementação de models isolados (já auditado em Models)
- definição de relacionamentos ORM (já auditado em Relacionamentos)
- migrations isoladas (já auditado em Migrations)
- validações de input (constraints)
- autenticação / RBAC
- middlewares
- controllers
- geração de PDF
- rotas públicas

---

# Fontes obrigatórias

Analisar:

- docs/especificacoes.md
- src/models/*
- migrations/*
- services que manipulam múltiplas entidades
- regras de negócio que cruzam entidades
- hooks que alteram estados
- constraints de banco de dados
- queries complexas (includes, joins, scopes)
- fluxo de criação/atualização/deleção de entidades

---

# Verificações obrigatórias

## 1. Integridade referencial global

- todas as FKs são respeitadas em todos os fluxos
- inexistência de registros órfãos
- consistência entre entidades dependentes
- ausência de inconsistências entre tabelas relacionadas

---

## 2. Consistência entre estados de entidades

- status de certificados coerente com regras do SRS
- eventos não quebram vínculos com usuários/tipos/certificados
- usuários não ficam vinculados a eventos inexistentes
- tipos de certificado não ficam órfãos

---

## 3. Integridade em soft delete

- entidades deletadas não quebram relações
- ausência de dangling references com deleted_at
- comportamento consistente de include com paranoid
- restauração não gera duplicidade ou inconsistência

---

## 4. Integridade de dados compostos

- JSONB (dados_dinamicos, valores_dinamicos) consistente entre entidades
- ausência de campos parciais ou incompletos
- coerência entre schema dinâmico e validação real
- consistência entre template e dados persistidos

---

## 5. Integridade de fluxo transacional

- criação de entidades múltiplas mantém consistência (ex: certificado + código + vínculo)
- ausência de estados intermediários inválidos
- falhas não deixam dados parcialmente persistidos
- coerência entre services que manipulam múltiplas tabelas

---

## 6. Integridade de regras de negócio

- regras de geração de código mantêm unicidade real
- constraints de negócio respeitadas no banco e na aplicação
- ausência de duplicidade lógica (mesmo dado com IDs diferentes)
- coerência entre status e comportamento funcional

---

## 7. Integridade multi-tenant (evento)

- isolamento correto entre eventos
- ausência de vazamento de dados entre eventos
- queries respeitam escopo de evento em todos os fluxos
- includes não rompem isolamento

---

## 8. Integridade de enumerações

- enums do banco coerentes com SRS
- ausência de valores inválidos persistidos
- transições de estado válidas (status lifecycle)

# Saída obrigatória

## 1. Matriz Consolidada de Achados

- ID
- entidade(s) envolvidas
- descrição
- evidências
- tipo
- severidade
- impacto
- requisitos violados
- destino recomendado

---

## 2. Problemas críticos de integridade relacional

Somente:
- quebra de consistência entre entidades
- orphan records críticos
- violação de multi-tenancy
- inconsistência de estado entre tabelas
- corrupção de dados por fluxo parcial

---

## 3. Backlog arquitetural

Separar em:
- curto prazo
- médio prazo
- longo prazo

---

## 4. Atualizações recomendadas no SRS

Somente quando:
- regra de integridade não estiver formalizada
- comportamento entre entidades estiver implícito
- fluxo transacional não estiver documentado

---

## 5. Itens para validação humana

- decisões sobre consistência eventual vs forte
- comportamento esperado em falhas parciais
- regras de restauração em cadeia
- comportamento de JSONB distribuído

---

## 6. Problemas sistêmicos de integridade

- inconsistência entre camadas (model/service/db)
- fragilidade em fluxos multi-entidade
- risco de corrupção silenciosa de dados
- divergência entre estado lógico e físico
